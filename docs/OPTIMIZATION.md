# Route Optimization

## Why not solve this exactly?

Finding a loop of *exactly* a target distance and elevation gain that
starts and ends at a given point is a constrained variant of the
orienteering / traveling-salesman problem on a real road graph — NP-hard
in general, and not something worth attempting to solve exactly for a
portfolio MVP. Instead this project uses a **generate-and-score**
heuristic:

1. Generate several geometrically different candidate routes.
2. Score every candidate against the request.
3. Return the best-scoring candidate.

This is explicitly documented as a heuristic approach, not a claim of
optimality (see `backend/app/services/optimization/loop_generator.py`
docstring).

## Candidate generation

For **loop** routes: `num_candidate_routes` (default 12, see
`app/config.py`) candidates are generated by placing two waypoints on a
circle whose circumference approximates the target distance, at angles
spread around the compass. Each candidate connects
`start -> waypoint1 -> waypoint2 -> start` using the chosen shortest-path
algorithm for each leg. Varying the base angle across candidates
produces different loop shapes to choose from.

For **out-and-back** routes: a single turnaround point is placed at
roughly half the target distance along a candidate bearing, and the
route is the shortest path there and back.

Waypoints are "idealized" circle-geometry points snapped to the nearest
real graph node — see "Limitations" below for what that means in
practice.

## Scoring function

```
score = distance_error_weight   * distance_error_norm
      + elevation_error_weight  * elevation_error_norm
      + difficulty_penalty_weight * difficulty
      + invalid_constraint_penalty * violation_count
```

Lower is better. All weights live in `app/config.py` (`Settings`), not
scattered through the code:

| Weight                        | Default | Purpose                                                        |
|--------------------------------|---------|------------------------------------------------------------------|
| `distance_error_weight`        | 1.0     | Penalize distance deviating from the target                     |
| `elevation_error_weight`       | 0.8     | Penalize elevation gain deviating from the desired amount        |
| `difficulty_penalty_weight`    | 0.2     | Small tiebreaker favoring flatter routes among similar candidates|
| `invalid_constraint_penalty`   | 5.0     | Flat penalty per violated hard constraint (see below)            |

`distance_error_norm` and `elevation_error_norm` are *fractional* errors
(`|actual - target| / target`), so the score is comparable across
requests of different sizes rather than being dominated by whichever
term happens to have larger absolute units.

### Hard constraints (violations)

A candidate is *scored* even if it violates a constraint (so the
optimizer can still return "the least bad" option rather than crashing
outright), but each violation adds a large flat penalty and is recorded:

- **Distance overshoot**: actual distance exceeds
  `target * (1 + max_distance_overshoot_fraction)` (default 35% over).
- **Elevation cap**: actual elevation gain exceeds `max_elevation_gain_ft`
  (either user-supplied, or a default of `2x` the desired gain).
- **Loop closure**: for loop routes, the route's end point is farther
  than `max_loop_closure_fraction` (default 15%) of the target distance
  away from the start point.

If literally no candidate is generated (e.g. an isolated single-node
graph), `NoValidRouteError` is raised and surfaced as an HTTP 422 — the
API never returns a fabricated "successful" route in that case.

## Known limitations

- **Waypoint snapping**: idealized circle-geometry waypoints are snapped
  to the nearest real graph node, which can pull a candidate
  significantly off the intended shape in sparse or irregular street
  networks (e.g. cul-de-sac-heavy suburbs, rural areas with few
  crossings).
- **Edge reuse**: candidates are not checked for overlapping edges
  between legs; a "loop" can, in principle, retrace some of the same
  street twice if the waypoint geometry pushes it that way.
- **No true TSP/orienteering solve**: this will not find *the* best
  possible loop for a given distance/elevation target, only the best of
  the `num_candidate_routes` generated. Increasing that number improves
  coverage at the cost of more shortest-path calls.
